> 이 문서는 기능을 **6개 카테고리**로 묶어 설명합니다.

각 기능은 **① 무엇을 해결하나 ② 어떻게 동작하나 ③ 관련 인증 통제 ④ 화면(캡처)** 순서로 적습니다.

## 카테고리 A. 운영 — 매일 쓰는 화면

### A-0. 실사용 시작 · 온보딩 카드
- **해결:** 데모는 쉬운데 "내 데이터로" 처음 띄우면 뭘·어디부터 할지 막막함(빈 화면).
- **동작:** `/admin` 첫 화면 맨 위에 **온보딩 카드**가 뜬다(admin·security 전용). 두 줄로 구성:
  - **첫 실행 체크리스트(5스텝):** ①소스 연결 ②경보 하나 처리 ③통제에 증적 연결 ④개인정보 흐름 스캔 ⑤감사 패키지 내보내기. 실데이터로 자동 판정되며 **"지금 할 일"** 이 파랗게 표시된다.
  - **커넥터 연결 상태:** 소스별 성숙도·연결 상태·마지막 수집. **pull 커넥터(Zabbix·Fleet)** 는 [연결 테스트] 버튼으로 현재 `.env` 설정을 **화면에서 즉시 검증**(파일 편집→클릭 확인).
- **결과 읽는 법(배지):**
  - 스텝: <span>초록 "완료"</span> · <span>파랑 "지금 할 일"</span> · 흐림 "대기".
  - 성숙도(정직 표기): **초록 "실검증"**(라이브 API로 검증됨) · **노랑 "부분(수신형)"**(고객 CI가 push) · 회색 "준비중"(미검증 스캐폴드).
  - 연결 상태: "연결됨"(수집 데이터 있음) · "설정됨(수집 대기)" · "수신 대기"(push 대기) · **빨강 계열 "미설정"**(+ 부족한 env 변수 나열).
  - 보안 태세: <span>초록 "보안 강화됨"</span> vs <span>빨강 "보안 취약(기본값 점검)"</span> — 기본 비밀번호·인증 꺼짐 등이 있으면 취약.
  - [연결 테스트] 결과는 버튼 옆에 **성공(초록)/실패(빨강, 원인 그대로)** 로 표시 — 실패 원인(인증·타임아웃·DNS)을 숨기지 않는다.
- **반영 위치:** 체크리스트는 실제 상태를 그대로 읽는다 — 예: 감사 패키지를 한 번 내보내면(⑤) 다음 조회부터 완료로 넘어간다. 5/5가 되면 카드 진행이 "완료"로 표시된다.
- **최소 설정:** `.env.minimal`(필수 변수만) 로 시작 → `docker compose up -d` → `/admin`.
- **통제:** 전반(실사용 진입·운영 가시성).

### A-1. 통합 대시보드
- **해결:** 자산·경보·취약점·할 일이 여러 도구에 흩어져 "지금 뭘 봐야 하지?"가 안 잡힘.
- **동작:** KPI 카드(전체/오프라인 호스트·24h 고위험 경보·Critical 취약점) + "오늘의 작업 큐(증적 공백)" +
  호스트 상태 표를 한 화면에. 오프라인·미조치가 위로 정렬.
- **통제:** 전반(운영 가시성).
<!-- [캡처 A1] /ui 첫 화면(KPI 카드 + 작업 큐 + 호스트 표) → docs/images/feat-a1-dashboard.png -->

### A-2. 경보 처리 (Alert Triage)
- **해결:** 경보를 왜 닫았는지 증적이 안 남음.
- **동작:** 접수 → 조사중 → 완료를 클릭으로. 소스 배지를 누르면 **원본 도구(Zabbix 등)로 딥링크**.
  모든 상태 변경이 **누가·언제·왜**로 기록. 탭을 열어두면 자동 갱신(주기 선택).
- **통제:** ISMS-P 2.11(사고 대응) 계열.
<!-- [캡처 A2] Triage 탭(경보 목록 + 상태 배지 + 소스 배지) → docs/images/feat-a2-triage.png -->

### A-3. 인시던트
- **해결:** 경보가 사고로 번지면 별도 관리·이력이 필요.
- **동작:** 경보를 인시던트로 승격, 담당자·조치자·타임라인 기록.
- **통제:** 사고 대응·기록.
<!-- [캡처 A3] 인시던트 상세 모달 → docs/images/feat-a3-incident.png -->

## 카테고리 B. 취약점 · 위험 관리

### B-1. 취약점 목록 (Trivy 등)
- **해결:** 스캐너 결과가 통제·증적과 연결되지 않음.
- **동작:** 호스트별 Critical/High 합계 + CVE별 **조치 계획/예외/만료일** + 변경 이력.
- **통제:** ISMS-P 2.10(취약점 점검·조치).
<!-- [캡처 B1] 취약점 탭(호스트별 합계 + CVE 목록) → docs/images/feat-b1-vuln.png -->

### B-2. 위험성 평가 (3×3 매트릭스)
- **해결:** "이 취약점이 우리에게 얼마나 위험한가"를 일관되게 판단·기록해야 함.
- **동작:** CVE별 **영향도(자산 중요도) × 발생가능성 = 점수(1~9)** + 위험처리 결정·잔여위험·수용기준(DoA) 자동 분류. (admin·security 전용)
- **통제:** 위험관리(위험 평가·처리).
<!-- [캡처 B2] 위험 매트릭스(3×3 격자 + 점수 배지) → docs/images/feat-b2-risk.png -->

## 카테고리 C. 컴플라이언스 — 통제 · 증적의 핵심

### C-1. 통제 카탈로그
- **해결:** ISMS-P·ISO 통제 수백 개를 스프레드시트로 관리하기 벅참.
- **동작:** ISMS-P 101 + ISO 27001:2022 93 = **194 통제**(한/영) 트리 + 이행상태 편집·영속.
  admin 직접 편집(추가/수정/삭제), 법령 텍스트 NLP 임포트. **검토완료/초안(draft) 라벨**로 정직하게 표시.
- **통제:** 통제 카탈로그 자체.
<!-- [캡처 C1] 통제 트리(도메인 펼침 + draft/reviewed 라벨) → docs/images/feat-c1-controls.png -->

### C-2. 증적 관리 · 출처 검증(Provenance)
- **해결:** "이 증적이 진짜인가, 언제 것인가, 누가 승인했나"를 심사관이 물음.
- **동작:** 통제에 증적을 연결하고 **승인·버전·content hash** 관리. 코드리뷰 증적은 **GitHub OIDC 서명으로 출처 검증**(위조 차단). 증적 신선도(오래된 증적) 표시.
- **통제:** 2.8(개발보안)·증적 무결성.
<!-- [캡처 C2] 통제 상세(증적 레코드 + 승인/버전/해시) → docs/images/feat-c2-evidence.png -->

### C-3. 통제 운영 거버넌스 (기준 버전 · 운영주기)
- **해결:** 기준이 개정(예: ISMS-P 2019→2023)되면 무엇을 다시 검토해야 하는지 관리해야 함.
- **동작:** 기준 버전 계보 · 버전 변경 영향분석(신규/삭제/변경 통제) · 연도별 운영주기(담당자는 승계, 판정은 초기화) · append-only 이벤트 원장(hash chain).
- **통제:** 관리체계 운영·지속개선.
<!-- [캡처 C3] 거버넌스 화면(기준 버전 목록 or 운영주기) → docs/images/feat-c3-governance.png -->

### C-4. 감사 제출 패키지 (Signed Evidence Bundle)
- **해결:** 심사 때 통제별 증적을 한 번에, 위변조 없이 제출해야 함.
- **동작:** 통제별 증적을 **PDF·CSV**로, 통째로 **ZIP**으로. ZIP에 **무결성 매니페스트 + 서명**을 넣어 "내보낸 뒤 수정하면 검증 실패"(tamper-evident). 위험 기반 감사 표본 추출·월별 증적 변경 보고도.
- **통제:** 증적 제출·무결성.
<!-- [캡처 C4] 증적 PDF 또는 ZIP 다운로드 결과 → docs/images/feat-c4-bundle.png -->

## 카테고리 D. 개인정보 (ISMS-P 3.x)

### D-1. 개인정보 처리흐름도
- **해결:** 개인정보가 수집→저장→이용→파기로 어떻게 흐르는지 매년 손으로 그림.
- **동작:** 코드 스캔(무료 규칙/유료 AI, **MORI는 코드 미보유**)에서 개인정보 항목·저장 위치를 뽑아
  **정보주체(고객) → 수집 → 저장(DB 테이블.컬럼) → 이용 → 파기** 플로우차트 + 제3자 제공(연계기관) 분기 생성.
  **어느 컬럼에 어떤 개인정보**인지 매칭 표 + 감사관용 PDF.
- **통제:** 3.1.1 수집 · 3.2.1 이용/제공 · 3.4.1 파기(자동 증적 승격).
<!-- [캡처 D1] 개인정보 흐름도 총괄 뷰(플로우차트) → docs/images/feat-d1-privacy-flow.png -->

### D-2. 처리방침 대조 · 개인정보 파일 개요
- **해결:** 실제 코드 흐름과 공개된 개인정보 처리방침이 어긋나는지 확인해야 함.
- **동작:** 선언한 처리방침 vs 실제 스캔 흐름을 대조해 갭 탐지. 파일(테이블/업무) 단위 개요표(정보주체 수·필수/선택·제3자·목적). DB 컬럼↔항목 매칭 CSV.
- **통제:** 3.x 개인정보 전반.
<!-- [캡처 D2] 처리방침 대조 결과 또는 개인정보 파일 개요표 → docs/images/feat-d2-privacy-policy.png -->

### D-3. 우려사항 · 암호화 표식
- **해결:** 어느 개인정보 컬럼이 암호화됐는지(법적 의무) 증적으로 남겨야 함.
- **동작:** 저장 컬럼의 **암호화 상태를 표식**(MORI가 암호화하는 게 아니라 상태 기록). 민감정보 암호화 미확인 등 우려사항을 **통제번호(2.7.1·3.3.1·3.3.4·3.4.1)에 매핑**.
- **통제:** 2.7(암호화)·3.3(제공/국외)·3.4(파기).
<!-- [캡처 D3] 우려사항·통제 매핑 섹션(PDF 안) → docs/images/feat-d3-concerns.png -->

## 카테고리 E. 개발보안 · 계정 · 소스 연동

### E-1. 코드 보안 리뷰 증적 (SDLC / 2.8)
- **해결:** 개발보안(코드 취약점)을 인증 증적으로 남겨야 함.
- **동작:** 고객 CI가 무료 Semgrep 또는 유료 Claude로 **기존 코드 전체**를 리뷰 → 결과를 MORI로 push.
  findings는 호스트 없는 경보로, 스캔 실행 자체는 **2.8 통제 증적으로 승격**(0건이어도 "통제 작동"). 출처는 **OIDC 서명 검증**.
- **통제:** ISMS-P 2.8.1·2.8.5 / ISO A.8.25·A.8.28.
<!-- [캡처 E1] 코드리뷰 스캔 이력(OIDC 검증 배지 + findings 수) → docs/images/feat-e1-code-review.png -->

### E-2. 계정 거버넌스
- **해결:** 퇴사자 계정·미승인 권한·휴면 계정이 서버·PC에 남아 있는지 점검해야 함.
- **동작:** 서버·PC 로컬 계정(osquery) × LDAP × 승인대장을 대조해 **퇴사자 잔존·미등록 특권·미승인 sudo·휴면**을 탐지. IP 팀/용도 CSV.
- **통제:** 2.5(접근권한 검토).
<!-- [캡처 E2] 계정 거버넌스 요약(발견 카드) → docs/images/feat-e2-accounts.png -->

### E-3. 소스 연동 (브라운필드)
- **해결:** 이미 쓰는 도구에 최소 설정으로 붙어야 함.
- **동작:** Zabbix(실 API 검증)·Fleet(자산)·Wazuh·Trivy·Loki를 `.env` 설정만으로 연결. Source freshness로 마지막 수집·상태 표시.
- **통제:** 자산·모니터링 소스.
<!-- [캡처 E3] Source freshness / 소스 상태 표 → docs/images/feat-e3-sources.png -->
